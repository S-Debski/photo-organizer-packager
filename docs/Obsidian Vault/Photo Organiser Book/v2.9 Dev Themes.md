## 1.1 Thumbnail Pipeline (Top Priority)

**Current state:**  
Thumbnails work and are correct.

**v2.9 improvement goals:**

- Faster perceived load
- Lower memory pressure
- No behavioural change

### Recommended steps

- Lazy-load thumbnails only when:
    - Tab is visible
    - Thumbnail enters viewport
- Cap concurrent image loads (e.g. 4–6)
- Abort thumbnail loads when navigating away

**Current risk:** large photo sets with GPS data.

Improvements:

- Skip `initMap` entirely unless:
    - Analyze complete
    - GPS data exists
- Chunk marker creation (batch rendering)
- Optional clustering above N points

3️⃣ Architectural Cleanups (Strategic, Surgical)
These are for preventing the next regression cycle.

3.1 Formalise Capability Gating

Make it explicit.
Instead of:

“Tab enabled because we’re here”

Prefer:

canAnalyze
canViewMap
canOrganize

Derived entirely from state.
This:

Improves readability
Avoids wiring regressions
Makes future UI changes safer


3.2 Job Lifecycle as a First‑Class Model
You already have polling and progress — v2.9 is a good time to unify it.
Define a small, explicit state machine:
idle → queued → running → finishing → complete | failed | cancelled

Benefits:

Cleaner progress UI
Clear cancellation semantics
Easier future features (pause, resume, retry)

This stays fully compatible with your Stability Contract.

3.3 Centralise Side‑Effect Entry Points
Earlier regressions came from implicit wiring.
In v2.9:

Centralise calls to:

initMap
loadThumbnails
job start/polling


Guard each with explicit preconditions
